# 移行で得た知見

## B1→Aで得た知見

1. **B1の原値と業務データを分ける。** 警告、対応先なし、開始前差分はB1原値として保全し、推測でAの業務在庫・請求・残高を作らない。
2. **差分は追加だけではない。** `changed`、`deleted`、既存伝票の明細差し替えがある。締め済み請求、在庫移動、月次が参照する明細を単純に削除・再作成しない。
3. **隔離DBで先に適用する。** Aの現状態と隔離DBの適用前指紋を比較し、同じ結果を確認してからAへ適用する。
4. **請求年月と出荷日を区別する。** 酒税は移出日、請求は請求年月で判定する。月またぎ出荷を出荷日だけで請求月へ混ぜない。
5. **Accessの入金は実入金だけではない。** 前月請求、増減訂正、手数料を含む符号付き台帳である。台帳の符号をそのまま実入金・充当に読み替えない。
6. **税額は履歴の保存値を尊重する。** 過去請求はAccess保存税額を保持し、税率混在の金額を一括で再計算しない。端数は伝票・請求単位の計算時点を確認して扱う。
7. **過去履歴を現在在庫へ二重反映しない。** 旧在庫履歴は監査用に保持し、ロット・場所・単位が確定できるものだけを業務在庫へ変換する。

## A→B2で得た知見

1. **完全昇格にする。** B2へ差分を重ねず、Aのコード、DB、帳票・添付を同じ時点で置き換える。B2だけの恒久修正は次の昇格で消える前提にする。
2. **成果物をハッシュで固定する。** Gitコミット、B1原本SHA-256、移行バッチID、DBダンプ、添付アーカイブ、アプリ配布アーカイブを一つのリリース記録にまとめる。
3. **WindowsとLinuxの改行を同一性の判断に使わない。** 展開済みのテキストファイルSHA-256は改行差で変わる。`git archive`などで作った配布アーカイブのSHA-256とGitコミットで確認する。
4. **日本語ファイル名をWindows側のtarで展開しない。** 添付・帳票に日本語パスが含まれる場合、Windowsの`tar.exe`では展開失敗の可能性がある。B2のLinuxコンテナ内で展開し、ファイル数と必要帳票を確認する。
5. **ホスト全体を止めない。** 対象のアプリ、Web、スケジューラだけを停止する。X99ホスト、DB、Redis、関係のないサービスは停止対象にしない。
6. **schedulerのイメージを事前確認する。** `docker compose up`が意図せずビルドや資格情報取得を試みることがある。B2には起動に必要なイメージを事前配置し、`--no-build`で起動できるかを受入試験に含める。
7. **B2の種別を明記する。** 非稼働テストB2では、明示承認と期限付き記録があれば事前バックアップを省略できる。本番候補・本番B2では省略しない。
8. **Web応答を実測する。** コンテナが`Up`だけでは足りない。Nginx経由のHTTP応答、アプリログ、migration状態、schedulerの稼働を確認する。

## 今後も守る判断基準

- 不一致を見つけたら、金額だけ合わせる修正を先にしない。原本、計算単位、請求年月、状態遷移、参照関係を確認する。
- 例外は一般承認に含めない。対象、操作、件数、影響、バックアップ、復元方法、承認者、期限を一件ごとに記録する。
- 検証で得た補正は、次回移行にも再現できる移行規則・テスト・照合規則として残す。

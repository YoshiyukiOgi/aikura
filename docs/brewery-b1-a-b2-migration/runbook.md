# 実行手順

## 0. 開始判定

次の項目がそろうまで、B1の抽出以外の作業を開始しない。

- 対象期間、対象業務、今回の基準バッチ、前回適用バッチを決める。
- B1のAccess原本パスと取得担当を決める。B1原本は更新しない。
- Aの現行Gitコミット、DB状態、未コミット変更を確認する。
- B1由来の変更・削除・過去月影響の扱いを決める確認者を決める。
- B2の種別を明記する。`test`なら現在のB2データを置換できるか、`production-candidate`なら事前バックアップと復元確認を必須とする。

## 1. B1からAへの移行

### 1-1. B1原本の採取

1. B1のAccessファイルを読取専用で作業領域へコピーする。
2. コピー元パス、取得日時、サイズ、最終更新日時、SHA-256を記録する。
3. 次を実行して、原本コピーからNDJSONと`manifest.json`を作成する。

```powershell
.\scripts\access\Export-AccessMigrationPackage.ps1 -SourcePath '<B1 Accessファイルのコピー>'
```

原本AccessそのものはGit、通常のアプリバックアップ、B2へ置かない。

### 1-2. Aへのステージングと差分計画

```powershell
.\scripts\access\Invoke-AccessDeltaMigration.ps1 -Mode Plan `
  -SourcePath '<B1 Accessファイルのコピー>' `
  -BaselineBatchId <前回適用バッチID>
```

確認するものは、ステージング結果、警告、差分CSV、対象期間、追加・変更・削除件数である。

### 1-3. 停止条件と隔離検証

次の場合はAへの適用を停止し、隔離DBで再現・照合してから個別承認を得る。

- 締め済み請求、売掛月次、酒税月次、消費税月次へ影響する差分
- 既存の請求明細、在庫移動、ロット月次が参照する出荷明細の差し替え
- 開始残高、開始在庫、過去年月の金額へ影響する差分
- ロット、場所、単位を確定できず業務在庫へ変換できない履歴
- B1原値とAの件数・数量・金額・税額が一致しないもの

適用前にAのDBをダンプし、隔離DBで同じスクリプトを実行する。適用スクリプトには対象バッチ、原本SHA-256、承認識別子、適用前の指紋、期待件数を固定する。

### 1-4. Aでの適用と照合

承認済みの差分だけを適用する。通常の適用は次の形式を使う。

```powershell
.\scripts\access\Invoke-AccessDeltaMigration.ps1 -Mode Apply -BatchId <承認済みバッチID>
```

適用後、[照合表](verification-matrix.md) のB1→A欄を記録する。未解決の差異は業務テーブルを推測で補正せず、B1原値、理由、次の判断を残す。

## 2. Aのリリース候補固定

1. Aで自動テストを実行し、失敗・除外の有無を記録する。
2. Gitのコミットを固定する。未コミットの業務コードは含めない。
3. AのDBダンプ、帳票・添付アーカイブ、アプリ配布アーカイブを同じ時点で作る。
4. 各成果物のSHA-256、サイズ、作成日時を記録する。
5. 次を実行してリリース記録を作る。

```powershell
.\scripts\migration\New-BreweryB1AB2ReleaseManifest.ps1 `
  -GitCommit '<Aのコミット>' `
  -B1SourceSha256 '<B1原本SHA-256>' `
  -MigrationBatchId <Aの移行バッチID> `
  -DatabaseDumpPath '<A DBダンプ>' `
  -StorageArchivePath '<帳票・添付アーカイブ>' `
  -ApplicationArchivePath '<git archive等のアプリ配布物>'
```

アプリ配布物は、作業ディレクトリのファイルハッシュを別OS上の展開済みファイルと直接比べない。Gitコミットと配布アーカイブのSHA-256で同一性を判定する。

## 3. AからB2への完全昇格

### 3-1. 共通の順序

1. [リリース記録](templates/release-record.md) の内容と実行対象を承認する。
2. B2の外部メール、外部API、印刷、キュー、スケジューラを検証用設定へ切り替える。
3. B2のアプリ、Web、スケジューラを停止する。ホストや関係のないコンテナは停止しない。
4. Aのアプリ成果物をB2へ配置する。B2固有の`.env`、Docker設定、秘密情報はAのものへ置き換えない。
5. AのDBダンプをB2へ復元する。
6. 帳票・添付をDBダンプと同じ時点のアーカイブから復元する。
7. マイグレーションを実行し、アプリ、Web、スケジューラを起動する。
8. B2の受入試験を行う。

### 3-2. テストB2の例外

テストB2で現在のデータが不要な場合は、B2事前バックアップを省略できる。ただし、リリース記録に次を残す。

- B2が非稼働のテスト環境であること
- 置換対象のDB、添付、コンテナ
- バックアップを省略する理由
- 承認者、承認日時、有効期限

この例外は本番候補B2や本番B2に使わない。

### 3-3. 本番候補B2の追加条件

- PostgreSQL、帳票・添付、B2固有設定、Docker・Web設定をサーバー外へ退避する。
- DBと添付を別環境へ復元し、復元できることを確認する。
- ロールバック手順と担当者を固定する。
- 実取引先へ送信されるメール、印刷、通知、API、決済連携を無効化したことを確認する。

## 4. B2受入試験と最終切替

B2では、ログイン、権限、出荷、取消、返品、在庫、請求、入金、帳票、酒税、消費税、監査ログを確認する。結果は[照合表](verification-matrix.md)とリリース記録に残す。

最終切替では、B1の入力を停止した直後に最終スナップショットを採取し、B1→Aの差分計画・照合をもう一度行う。未承認差異があればB2を本番化しない。

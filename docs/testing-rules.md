## 第6段階追加テスト

第6段階では、製造ロット、販売商品と製造ロットの関連、ロット別在庫、ロット引当、在庫予約、受注、出荷指示、品出をFeature Testで確認する。受注作成、出荷指示作成、品出作成は、それぞれ在庫移動、請求、売掛を発生させないことを検証対象に含める。

## 第7段階追加テスト

第7段階では、品出から出荷伝票ドラフトへの接続、受注から請求ドラフトまでの一気通貫、品出取消、出荷指示取消、受注取消、取消逆順フロー、品出由来出荷伝票と在庫予約・ロット引当・出荷確定の接続、品出由来出荷伝票の取消方針をFeature Testで確認する。取消系は、履歴を削除しないこと、理由が必須であること、二重取消が拒否されること、後続工程が存在する場合は直接取消できないことを検証対象に含める。

第8段階では、画面・API・権限制御をFeature Testで確認する。画面またはAPIはService層の業務判断に従い、税額、酒税、在庫、売掛、月次残高を画面側で確定計算してはならない。権限不足、締め済み期間、状態不整合、入力不備、二重送信を検証対象に含める。

8-1ではAPIルート登録、共通JSON応答、ControllerからServiceを呼び出す境界、APIルートカタログをFeature Testで確認する。

8-2ではAPI権限制御をFeature Testで確認する。未ログイン、権限不足、無効ユーザー、権限ありユーザーの応答を検証対象に含める。

8-3では受注APIをFeature Testで確認する。受注作成、一覧、詳細、取消、権限不足、入力検証を検証対象に含める。

8-4では出荷指示APIをFeature Testで確認する。出荷指示作成、一覧、詳細、取消、受注残更新、権限不足、入力検証を検証対象に含める。
8-5では品出APIをFeature Testで確認する。品出作成、一覧、詳細、取消、出荷指示明細の品出済数量更新、出荷指示状態更新、権限不足、入力検証を検証対象に含める。品出作成時点で在庫移動、請求、売掛を発生させない方針は既存Serviceテストと合わせて確認する。
8-6では出荷伝票APIをFeature Testで確認する。出荷伝票ドラフト作成、価格適用、確定、一覧、詳細、取消、権限不足、入力検証を検証対象に含める。出荷確定時の価格スナップショット、消費税、酒税見込額、在庫移動は既存Serviceテストと合わせて確認する。輸出免税の優先判定は未実装のため、実装時には `docs/tax-export-rules.md` の受け入れ条件を必須テストに追加する。
8-7では在庫APIをFeature Testで確認する。現在庫照会、ロット在庫照会、出荷明細への在庫予約、出荷明細へのロット引当、権限不足、入力検証を検証対象に含める。在庫予約とロット引当では在庫移動を発生させず、出荷確定時に在庫移動へ接続する方針は既存Serviceテストと合わせて確認する。
8-8では請求・入金APIをFeature Testで確認する。請求ドラフト作成、請求確定、請求取消、入金予定作成、入金登録、入金取消、売掛残高照会、権限不足、入力検証を検証対象に含める。請求金額、消費税、入金予定、入金消込、売掛残高は既存Serviceテストと合わせて確認する。過入金は、請求残額までを消込し、超過額を `unapplied_amount` として `review_required` にすることを確認する。複数請求への一括配分と未消込残高の再配分は未実装であり、実装時に別テストを追加する。
8-9では税務APIをFeature Testで確認する。酒税月次申告ドラフト作成、酒税月次申告確定、消費税月次申告ドラフト作成、消費税月次申告確定、一覧、詳細、権限不足、入力検証を検証対象に含める。酒税移出集計、酒税額、消費税集計、消費税額、確定額は既存Serviceテストと合わせて確認する。
8-10では月次締めAPIをFeature Testで確認する。在庫月次残高ドラフト作成、在庫月次残高確定、売掛月次残高ドラフト作成、売掛月次残高確定、売掛月次残高締め、一覧、権限不足、入力検証を検証対象に含める。在庫数量、売掛予定額、入金額、未回収額、締め後の業務データ更新禁止は既存Serviceテストと合わせて確認する。

9-4では消費税申告帳票をFeature Testで確認する。確定済み消費税月次申告から帳票ファイル、出力履歴、ファイルパス、ファイルサイズ、SHA-256、出力理由、監査ログを生成できることを検証対象に含める。同一消費税月次申告の再発行では既存ファイルを上書きせず別ファイルとして保存することを確認する。未確定消費税月次申告、未対応形式からの帳票生成は失敗することを確認する。
9-5では売掛月次残高帳票をFeature Testで確認する。確定済みまたは締め済み売掛月次残高から帳票ファイル、出力履歴、ファイルパス、ファイルサイズ、SHA-256、出力理由、監査ログを生成できることを検証対象に含める。同一年月の売掛月次残高帳票の再発行では既存ファイルを上書きせず別ファイルとして保存することを確認する。未確定売掛月次残高、未対応形式からの帳票生成は失敗することを確認する。

第10段階では、非同期バッチ・運用をFeature TestまたはIntegration Testで確認する。ジョブ成功、失敗履歴、再実行、冪等性、監査ログを検証対象に含める。

第11段階では、検索・一覧・実務UXをFeature Testで確認する。検索条件、状態別一覧、取引先別、商品別、ロット別、監査ログ検索を検証対象に含める。

# テスト方針

## 1. 位置づけ

この文書は、Feature Test、Unit Test、業務ロジック検証、回帰テストの方針を定義する。

中核業務ロジックはテストなしで実装しない。

## 2. 基本方針

1. DB、Service、状態遷移、計算結果を中心にテストする。
2. UIの見た目より、業務整合性を優先してテストする。
3. 確定済みデータが変わらないことを必ずテストする。
4. 禁止操作が失敗することもテストする。
5. 境界値、丸め、締め済み、権限不足を重点的にテストする。

## 3. Feature Test 必須領域

以下はFeature Testを必須とする。

* 取引先作成・無効化
* 商品作成・無効化
* 価格決定
* 出荷伝票作成
* 出荷伝票確定
* 出荷伝票取消
* 確定時スナップショット
* 税計算
* 酒税計算
* 在庫更新
* ロット引当
* 請求確定
* 入金消込
* 過入金の未消込残高
* 月次締め
* 締め済みデータ更新禁止
* 帳票出力
* 監査ログ

## 4. Unit Test 対象

以下はUnit Testで検証する。

* 丸め処理
* 単位換算
* 価格優先順位
* 税ルール判定
* 酒税計算式
* 状態遷移可否判定
* 日付計算

## 5. テストデータ

1. テストデータはテスト内またはFactoryで作成する。
2. テスト間でデータ依存しない。
3. 価格、税率、酒税、在庫数量は期待値が分かる小さな値にする。
4. 日本語名称、旧コード、カナ検索なども必要に応じて含める。

## 6. 確定済みデータのテスト

以下を必ず検証する。

1. 伝票確定時に単価、税率、酒税、商品名、容量、Alc%、丸め方式が保存される。
2. 確定後に商品マスタを変更しても、過去伝票の表示値が変わらない。
3. 確定後に価格表を変更しても、過去伝票の単価が変わらない。
4. 確定後に税ルールを変更しても、過去伝票の税額が変わらない。

## 6-1. 返品・戻入の追加テスト

返品・酒税戻入は未実装である。実装時は `docs/returns-and-tax-adjustments.md` の受け入れ条件に加え、税率改正後の部分返品が元請求明細の税率を使うこと、戻入が元出荷明細の酒税スナップショットを使うこと、確定済み月を直接更新しないことをFeature Testで確認する。

## 7. 状態遷移のテスト

以下を検証する。

* 許可された遷移は成功する。
* 禁止された遷移は失敗する。
* `status` の直接変更ではなくService経由で処理される。
* 締め済みデータは直接変更できない。
* 状態遷移時に監査ログが残る。

## 8. 在庫テスト

以下を検証する。

* 在庫移動が正本として記録される。
* 現在庫が正しく更新される。
* 在庫不足時に出荷または引当が失敗する。
* 棚卸差異は在庫移動として記録される。
* 現在庫残高だけの直接修正を許可しない。

## 9. 月次締めテスト

以下を検証する。

* 売掛月次残高が締め時点で保存され、翌月繰越根拠になる。
* 在庫残高が締め時点で保存される。
* 酒税、消費税、請求残高が確定される。
* 締め後の直接変更が失敗する。
* 調整処理が翌月以降に記録される。
* 確定済みまたは締め済みの月次残高・税務申告から帳票を生成でき、未確定データからの帳票生成は失敗する。

## 10. 実行コマンド

Docker環境では以下を使う。

```powershell
docker compose run --rm test php artisan test
```

特定テストだけ実行する場合は以下とする。

```powershell
docker compose run --rm test php artisan test --filter=HealthCheckTest
```

## 11. 完了条件

実装タスクは以下を満たして完了とする。

* Feature TestまたはUnit Testが追加されている。
* 既存テストが通る。
* 禁止操作の失敗ケースが検証されている。
* 監査ログが必要な操作ではログ作成が検証されている。

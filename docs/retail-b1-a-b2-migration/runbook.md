# 小売B1-A-B2 実行手順（準備版・未実行）

[酒蔵側の実行手順](../brewery-b1-a-b2-migration/runbook.md) の段階構成を採用する。本書は将来の実行に備える手順であり、現在の「まだ実行しない」という利用者指示を変更しない。今回は新規抽出・ステージング・取込・復元・デプロイを実行しない。

工程②は玉川小売を対象として完了。[詳細調査結果](phase2-investigation.md) を参照。A/B2は酒蔵と同じDB・アプリを共有し、小売の構造・依存一覧は24表。Aには小売migration1件が未適用。工程③で玉川の対象行・共有行・採番の扱いを固定する。桜浜は今回対象外であり、会計原本確認は次回へ延期。

## 0. 開始判定

各段階の実行前に、[リリース記録](templates/release-record.md) に対象・操作・証跡を具体化する。

- 今回のB1は玉川小売の `Tamagawa-xp.accdb`。所在・取得担当・証跡を管理する。Itaroは玉川の商品・蔵連携の参照資料として扱う。
- 対象は玉川小売（maru／会社ID 1）の顧客・仕入先・商品・価格・売上・返品・請求・入金・売掛・発注。桜浜は別途対応。在庫取込と蔵から小売への在庫振替は含めない。
- 期間は酒蔵側と同じ。既存記録の取引開始2026-07-01、開始売掛2026-06-30を直近の酒蔵リリース証跡と照合し、過去履歴下限・取得締切も記録する。
- [データ対応](data-mapping.md) の玉川の会社コード・商品区分・旧蔵連携先33を取込仕様へ反映する。Tamagawaの請求・入金・売掛・発注の表現は工程②で調査済み。変換規則を工程③で具体化する。
- 保全不要の回答は玉川専用の実取引・設定に限定する。初回再構築の対象行・件数・参照関係を確定し、実行指示までは削除・初期化しない。桜浜・他社・共有行・酒蔵・認証・監査証跡を保持する。
- AはこのPCのDocker内の小売、B2は `ssh kura` 接続先PC内の小売。所在は確定済みとして、実効DB・スキーマ・コンテナ、共有認証・採番・添付と酒蔵参照を調査する。
- 小売専用取込・差分処理、在庫非管理、履歴取込時の受注再送抑止を実装・検証する。未整備の処理を酒蔵用コマンドで代用しない。
- 復元単位は酒蔵と分離した小売単位で確定。B2種別・稼働状況・分離対象を記録する。確認体制は現時点で未設置であり、準備は継続する。実行・照合・復旧の担当と判断方法は実行段階までに設定し、未記入のまま実行済み・承認済みとしない。
- 利用者が具体化した対象段階の実行を指示していることを確認する。過去の酒蔵移行の承認・例外は引き継がない。

## 1. B1からAへの移行

### 1-1. 読取専用スナップショットと抽出

1. 取得時点の一貫性を確保してTamagawa原本をコピーし、原本を変更しない。対象取引の締切と、商品・蔵連携に用いる参照資料の取得時点を記録する。
2. コピー元識別、取得日時、サイズ、更新日時、SHA-256、取得担当を記録する。
3. 既存 `scripts/access/Export-AccessMigrationPackage.ps1` を原本コピーに対して使用する計画とし、対象テーブル・リンク・クエリの網羅性を事前確認する。
4. 原本ごとに抽出manifest、各ファイルのSHA-256、行数・旧ID・参照関係を検査する。原本・顧客明細はGitや通常ログへ置かない。

現在ある2026-09-22の抽出パッケージは調査用証跡である。最新原本確認や初回基準バッチの指定なしに適用対象へ格上げしない。

### 1-2. Aへの初回ステージング・差分計画

1. 初回は確定したTamagawa原本・玉川・期間・変換規則で専用ステージングを作り、玉川データの再構築範囲を確認する。玉川の酒蔵側既存取引を再作成しない対応を固定し、桜浜の取引を含めない。
2. 2回目以降は前回適用済み小売バッチと比較し、原本識別子・元テーブル・旧ID・内容ハッシュで `new / changed / deleted / unchanged` を分類する。
3. 件数・数量・金額・税額、既存設定の更新、請求・消込・締め済み期間への影響、対象外と保留理由を差分一覧へ出力する。
4. 開始日前の履歴は酒蔵側と同じ参照専用方針とし、現在売掛・請求・酒蔵受注に再計上しない。

Tamagawaの基準バッチを記録する。酒蔵側既存取引へ参照を付ける場合は関連キーと一致項目を残し、原本間の番号一致だけで結合しない。桜浜の販売・会計データは今回取り込まない。

**小売専用ステージング・差分コマンドは未整備。** `Stage-AccessMigration.ps1` と `Invoke-AccessDeltaMigration.ps1 -Mode Plan` は、酒蔵用 `aikura:access-stage` 等を呼びAへ書き込む。単なる読取プレビューとして使わない。`Apply` も酒蔵向け処理であり、小売原本へそのまま適用しない。

### 1-3. 差分確認と隔離検証

- `changed`、`deleted`、締め済み期間への `new`、開始残高・既存消込への影響は自動適用しない。対象・訂正方法・期待結果を記録する。
- Aの対象DB・添付を同じ時点でバックアップし、隔離した小売・酒蔵DBへ復元して検証する。通常接続と `retail` 接続の両方を隔離する。
- 同じパッケージの2回適用、途中失敗と再開、別接続での部分成功、既存行の意図しない変更を確認する。
- 在庫非管理の会社では販売・訂正・返品・取消で小売残数・在庫移動を作成更新しない。既存在庫を削除・ゼロ化しない。
- 履歴から酒蔵受注・出荷・請求・在庫を再作成しない。外部商品以外の将来の連携ロジックは隔離環境で確認し、実機・外部送信は行わない。

### 1-4. Aでの適用と照合

1. 検証結果、Aバックアップ、原本ハッシュ、対象バッチ、差分一覧、適用前状態、期待件数を固定する。
2. 対象と承認が一致する小売専用処理だけを実行する。直前状態が隔離検証時から変わっていれば再計画する。
3. [照合表](verification-matrix.md) のB1→A値と証跡を記録する。未承認の数量・金額差、旧ID重複・参照切れ・想定外の酒蔵更新は0件とする。
4. 差異を金額合わせで補正しない。Aの月次・請求・帳票検証は適用完了後の別操作とし、移行から自動確定・締めを起こさない。

## 2. Aのリリース候補固定

1. 小売と酒蔵の依存範囲のテスト・照合結果を記録する。業務DBをテスト接続に使わない。
2. 配布するGitコミットとmigration状態を固定する。未コミットの業務コードを配布対象に混ぜない。
3. 書込みを止める等の整合確保方法を決め、対象DBダンプ、帳票・添付、アプリ配布物を一組として採取する。
4. 各成果物のパス・サイズ・作成日時・SHA-256と対象DBの役割を [リリース記録](templates/release-record.md) へ記載する。
5. 小売のみの分離復元範囲と復元順序を固定する。共有DBの場合は小売の対象表・スキーマ・採番・参照依存を明示し、酒蔵側の行・スキーマを変更しない方式を検証する。別DBの場合も酒蔵参照IDの対応を確認する。共通アプリコード・認証・ストレージの影響も検証する。

酒蔵用 `New-BreweryB1AB2ReleaseManifest.ps1` の成果物固定方式を見本とする。小売の記録形式はテンプレートに定義済みだが、自動manifest生成は未整備。スクリプト名・承認済みハッシュ・成功結果を仮作成しない。

## 3. AからB2への完全昇格

### 3-1. 開始条件と共通の順序

B2は `ssh kura` 接続先PC内の小売とし、酒蔵側は復元対象に含めない。A/B2間の酒蔵参照IDや共有コードの互換性を先に照合する。現構成から分離復元できることを確認できなければ、分離設計を完成させるまで適用しない。酒蔵を含む全DB復元やB2への差分継ぎ足しへ切り替えない。

1. リリース記録の対象・成果物・操作・復旧方法と実行指示を照合する。
2. B2の実メール・実印刷・外部API・通知を抑止し、Web・Queue・Scheduler等の対象書込み経路を停止する。内部の酒蔵受注サービスも考慮する。
3. 対象DB・帳票・添付・B2固有設定・Docker/Web設定を事前保全する。ホストや無関係なサービスは停止しない。
4. Aと同じコミットの配布物を配置する。B2の秘密情報・環境設定をAの設定で上書きしない。
5. 玉川の確定した対象行・必要な帳票等を、同じAリリースの成果物から完全復元する。小売全表を全行置換しない。会社列のない子表は親IDで範囲を決め、共有行の競合は自動上書きしない。採番は他社のIDを含む衝突防止条件を守り、桜浜・他社・酒蔵・共有認証等の対象外が不変であることを確認する。
6. DB参照整合、migration状態、配布物ハッシュを確認する。追加migrationが必要なら候補固定時に定めたものだけを実行する。
7. Webを検証用設定で起動し、HTTP・ログ・権限を確認する。Queue/Schedulerは意図しない更新がないことを確認した範囲だけ再開する。
8. B2受入結果を記録する。修正が必要ならAで再現・修正し、新しいリリースとして完全昇格する。

### 3-2. テストB2の例外

非稼働テストB2の現在データが不要な場合のバックアップ省略は、酒蔵見本と同様、対象・理由・影響・代替確認・承認者・期限を [例外記録](templates/exception-record.md) へ残す。本パッケージでは省略を承認済みとしない。本番候補・本番には適用しない。

### 3-3. 本番候補・本番B2

DB・添付・設定の復元可能な事前バックアップをサーバー外へ保管し、別環境での復元確認を行う。実行・復旧担当と停止時間を固定する。今回の実機・外部連携試験除外は、バックアップ・復元確認の省略を意味しない。

## 4. B2受入試験と将来の最終切替

受入対象はログイン・会社切替・権限、顧客・商品、販売・訂正・返品、請求・入金・売掛、発注、帳票表示、監査、在庫非管理、内部の酒蔵連携判定。データ比較はB1→AとA→B2を分けて記録する。POS端末・バーコード・レシートプリンタ・決済端末・メール等の実機・外部連携試験は今回対象外。

最終切替は将来の別段階。B1入力停止時刻、酒蔵側との境界、最終差分の締切を決め、B1停止→最終取得→A適用・照合→候補固定→B2完全昇格→受入→業務正本切替の順で行う。今回対象外の試験は未検証のまま記録し、本番切替の条件はその段階で定める。B1と証跡は読取専用で保全する。

## 5. 停止・復旧

ハッシュ・件数不一致、会社や旧IDの誤対応、未承認差異、復元単位不明、想定外の在庫更新・受注作成があれば次段階へ進まない。

- A適用失敗: 書込みを止め、処理単位のロールバック結果を確認する。複数接続の部分成功があれば、事前に定めた整合するバックアップへ戻して再計画する。
- B2受入失敗: Webの業務開放とジョブ再開を止め、小売の旧アプリ・対象DB範囲・帳票・添付・設定を一組で復元する。共有部分を巻き戻す場合の影響は事前に設計し、酒蔵データを復元に巻き込まない。復元後の照合結果を記録する。
- 業務再開後に新規取引が発生した場合: 事前バックアップへ単純に戻さず、新規取引保全を含む別の復旧計画を作る。

失敗原因・差異・復旧結果をリリース記録へ残し、Aで再現できるコード・移行規則・テストとして恒久化する。

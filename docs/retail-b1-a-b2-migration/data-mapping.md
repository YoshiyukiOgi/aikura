## 3. 優先して解消する実装差

### Tamagawa原本と酒蔵側の既存取引

- 対応キーは、継続的に同じ原本を識別する論理識別子＋元テーブル＋旧IDを基本とする。取得回のSHA-256・バッチIDは証跡として別に保持し、差分のたびに別取引として増やさない。
- 玉川maru/会社1に対象を固定し、桜浜や他の酒蔵取引を取り込まない。Itaroは玉川の商品・蔵連携先等の参照資料として扱う。
- 同じ取引が酒蔵側に取込済みかを旧ID・明細ID・金額・状態で照合する。小売側の必要な表現と酒蔵側の既存業務データの対応を設計し、酒蔵受注・出荷・請求・入金・在庫を再生成しない。
- TamagawaとItaroで番号が一致するだけでは同一取引とみなさない。原本間の販売・請求・入金の対応は、明示的な関連キーと照合結果を残す。対応不明は保留として分類する。
- 玉川専用の既存データは初回再構築を計画できる。桜浜・他社・共通マスター・酒蔵・認証・証跡は保持し、会社列のない子表は玉川の親IDから対象を決める。共有行・採番の扱いと対象件数を工程③で固定し、実行指示までは変更しない。

### 在庫非管理

現行 `inventory_sales_policy` の選択肢は `strict_stock` と `allow_negative_order`。後者でも `CreateRetailSaleService` は在庫残数を更新し移動を記録する。`AdjustRetailSaleService` の訂正・取消・赤伝も在庫を動かす。

準備する設計は、対象会社で在庫非管理を明示でき、販売・訂正・返品・取消が小売在庫を作成・更新しないこと。在庫0でも通常販売ができ、残数を前提にした補充提案を適用しない。商品マスター、販売数量、返品数量、発注履歴は保持し、発注業務そのものを削除しない。共用商品への影響と他会社の在庫管理を分離する。既存の残数をゼロ化する処理は行わない。

### 外部商品以外の酒蔵受注連携

現行 `RetailBrewerySaleSyncService::linesFromSaleItems` は `procurement_source=brewery`、蔵商品IDあり、蔵商品が販売停止・削除状態でない明細を対象にする。それ以外を黙って読み飛ばす動作が、今回の対象条件と一致するか検証が必要。

| ケース | 準備する判定 |
| --- | --- |
| 外部商品のみ | 酒蔵受注を作らない |
| 外部商品と蔵商品の混在 | 蔵商品の明細だけを対象にする |
| 非外部だが蔵商品未対応・不明区分 | 対応未解決として報告し、連携完了扱いにしない |
| 販売停止・削除済み商品 | 履歴参照と今後の販売可否を区別。IDを推測して送らない |
| 入金用疑似商品 | 実際の業務意味を確認し、入金を商品売上として連携しない |
| 移行する過去販売・返品 | 受注再送なし。酒蔵側に存在する取引との参照・重複を照合する |

外部商品を含むすべての小売業務データは移行対象であり、「外部商品は移行対象外」ではない。今回の実機・外部連携試験除外も、この業務上の連携対象条件を変更しない。

### 開始残高・請求・入金・履歴

酒蔵側の既存手順は取引開始2026-07-01、開始売掛2026-06-30。工程②の実DB調査では6月からの出荷・入金も残り、開始残高行の日付は2026-07-01だった。6月の参照履歴と7月の開始残高を区別し、二重計上を防ぐ対象条件を工程③で固定する。酒蔵側の特定取引先「玉川小売」の内部売掛残高を、小売個人顧客の開始残高としてコピーしない。

開始残高表現、請求状態、入金・消込の元データを確定するまで、販売ヘッダー数と数量×単価だけで請求・売掛を生成しない。元値・変換規則・照合差異を残せる専用取込仕様を用意する。

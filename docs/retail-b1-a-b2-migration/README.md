## 3. 準備作業の順序

### P0: 原本と環境の対応を決める

- 第1節を埋め、B1／A／B2と会社・店舗の対応表を作る。
- 接続URLによる上書きも含め、小売と酒蔵の実効DB・スキーマ、共有認証・採番・帳票・ストレージの依存を確認する。秘密の値は記録しない。
- A/B2の所在と分離復元の方針は確定済み。共有箇所があれば酒蔵側を保全する分離方法を設計し、酒蔵を含む全DB復元へ切り替えない。

### P1: データ対応表を作る

既存のTamagawaとItaroの抽出資料を基に、各対象について「原本識別子・元テーブル・旧主キー・会社／店舗・対象期間・移行先・変換規則・除外理由・照合基準」を定義する。現物未確認のテーブル対応を推測で確定しない。

対象は、会社・顧客・仕入先・商品・単位・価格・税区分、販売と明細、返品・取消、関連する納品、請求、入金・消込・未充当、開始売掛、発注（完了履歴・未処理を区分）、帳票・添付、採番、酒蔵側との参照ID。在庫残数・在庫移動の移行と蔵在庫の振替は対象外。

- 開始残高方式と未決済伝票方式のどちらを使うか決め、売掛を二重計上しない。
- 販売・返品履歴の取込から、小売在庫の作成・更新や蔵在庫への振替を発生させない。
- 現金販売と掛売、返金と赤伝、酒蔵内部取引と小売顧客への売上を区別する。
- 過去の価格・税額・端数・請求方法は原本保存値と規則を確認する。
- 酒蔵側のロット在庫管理は維持する。今回の小売在庫非管理を酒蔵在庫管理の停止へ広げない。

### P2: 不足する移行処理の仕様を決める

- 取込前の件数・旧ID・参照切れ・ハッシュ検査と、書き込まない差分出力。
- 原本識別子＋元テーブル＋旧IDから移行先IDを追跡できる対応記録。
- 玉川のItaro旧連携先33と酒蔵側既存取引への対応。結合根拠を記録し、原本間の番号一致だけで結合しない。桜浜の抽出仕様は次回へ延期。
- `new / changed / deleted / unchanged` の分類。変更・削除・締め済み期間への追加を自動適用しない。
- 再適用しても件数・金額・在庫・売掛・酒蔵受注が増減しない仕組みと、中断時の復旧単位。
- 履歴の取込では販売サービスによる再計算・在庫移動・受注送信・請求確定を起こさない仕組み。
- 顧客取込の会社間衝突、既存設定上書き、旧ID検査、ハッシュ検証の対応。
- 玉川小売の在庫非管理。販売・訂正・返品・取消で小売残数・移動を作らず、在庫不足判定や残数による補充提案を適用しない設計。発注自体は移行対象として保持し、他社設定は変更しない。
- 外部商品以外を明細単位で酒蔵連携対象にする。商品ID未対応・販売停止等の非外部商品を黙って連携対象外にしない。履歴取込時の再送防止を別に設ける。
- 小売単位の整合スナップショット・分離復元手順。現構成が共有DBなら対象表・スキーマ・参照関係を切り分ける設計が必要。別接続をまたぐ処理の部分成功も検証対象にする。

工程③で上記の主要処理を専用作業コピーに実装した。稼働Aの業務コードは変更していない。実装済み範囲と残作業は [工程③記録](phase3-preparation.md) を参照する。

### P3: 将来の隔離検証と受入基準を定義する

[照合チェックリスト](verification-matrix.md) を使い、固定した原本コピーと隔離した小売・酒蔵DBで検証する計画を作る。旧ID重複、参照切れ、想定外の酒蔵更新、未承認の金額・数量差異は0件を合格条件とする。

既存Featureテストは `RefreshDatabase` を使うため、実行前に通常DBと小売DBの両接続が廃棄可能な専用テストDBであることを確認する。業務DBを使って試験しない。

### P4: A→B2昇格案と復旧案を固定する

既存方針の「検証済みコード・DB・帳票等を一組にする」原則を、小売と酒蔵を分離した復元単位に適用する。このPCのDocker内のAから、`ssh kura` 接続先PC内のB2小売へ昇格する。分離は利用者が指定した方法であり、現環境がすでに物理的な別DB・別アプリであることを確認したという意味ではない。共有DB・共通コード・認証・ストレージがある場合は、対象表・参照ID・互換性・対象外の不変確認を含む分離設計を先に完成させる。酒蔵側は復元対象外とし、連携IDを照合するための参照対象とする。小売の対象範囲は完全置換し、B2への差分継ぎ足しで代用しない。

リリース記録には、原本ごとのSHA-256、対象会社・期間、移行バッチ、Gitコミット、全対象DBダンプ・帳票等のハッシュ、実効接続先、保持対象、照合結果、バックアップ、復元方法、連携抑止方法、実行・復旧担当を記載する。B2固有設定と秘密情報はAの設定で置換しない。実機・外部連携試験は今回対象外として記録し、実機受入済み・実取引連携検証済みとは扱わない。

`New-BreweryB1AB2ReleaseManifest.ps1` は酒蔵名と単一DBダンプを前提とする。小売の記録項目は [リリース記録](templates/release-record.md) に定義する。小売用の自動manifest生成は未整備であり、酒蔵用ツールをそのまま使った記録で代用しない。

## 4. 実行へ進む条件

準備文書の作成は移行実行の承認ではない。P0〜P4の未確認事項・設計差を解消し、対象・操作・影響・復旧方法が具体化した時点で、利用者の実行指示を受ける。それまでは抽出・取込・リハーサル・A/B2変更へ進まない。

業務データ変更の前に新しい証跡と復元可能なバックアップを用意する計画とし、過去のバックアップ省略承認は流用しない。原本や対象DBが不明、未承認差異がある、連携を隔離できない、復元できない場合は実行しない。

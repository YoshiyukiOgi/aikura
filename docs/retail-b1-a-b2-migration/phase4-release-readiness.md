# 後工程準備 玉川小売の配布版固定・実行準備（2026-09-23）

**本書は工程⑦以降で用いる準備資料として、玉川小売の実装候補をレビューし、配布候補とA・B2それぞれの事前確認・反映・復旧手順を確定したものである。** 工程④は別の [B1取得・抽出](phase4-extraction.md) として実行する。この準備では A/B2 への接続、コード配布、migration、取込、設定変更、実データ復元は一切行っていない。桜浜酒店は対象外のままとする。

## 1. 配布候補

- 作業場所は通常の A にマウントされるフォルダーと分離した `tamagawa-phase3` 作業コピーである。配布時は、この作業コピーを Git の一つのコミットとして固定したものだけを使う。
- 追加する migration は次の 2 件である。どちらも先に A で未適用だった既存 migration を適用してから使用する。
  1. `2026_09_21_010000_add_retail_purchase_order_cancellation_and_document_sequences.php`（既存、A で未適用）
  2. `2026_09_23_000001_add_retail_company_brewery_partner.php`
  3. `2026_09_23_000002_create_retail_legacy_releases.php`
- 取込・復元コマンドは、書込み時に `--apply`、成果物ハッシュ、取込先直前ハッシュを全て要求する。出力先は新規ファイルのみ許可し、既存の証跡を上書きしない。
- 取込対象の蔵取引先・蔵商品は、Laravel の既定接続ではなく、反映先の `retail.database.connection` から検証する。A/B2 が将来別接続になっても、別のDBを誤って検査しないためである。
- 隔離環境で 74 tests / 580 assertions が成功した。保存済みの原本で作った再計画は 58,314 識別要素について new=0、changed=0、deleted=0、unchanged=58,314 である。原本計画・対応表・復元成果物は個人情報を含むため、Git には含めない。

## 2. 実行前に固定する記録

実行を開始する承認を得た後、A と B2 で別々に、次の項目を [リリース記録テンプレート](templates/release-record.md) に記録する。A の記録を B2 の復元先確認値として流用しない。

| 項目 | A | B2 |
| --- | --- | --- |
| 配布コミット・作業ツリーがcleanであること | 記録 | 記録 |
| 配布ファイル・原本パッケージ・計画・対応表のSHA-256 | 記録 | A成果物とB2事前成果物を記録 |
| 3 migration の `migrate:status` | 適用前後を記録 | 適用前後を記録 |

| `retail:tamagawa-release export` のハッシュ | 取込前・取込後を採取 | 復元直前・復元後を採取 |
| 実行者・照合者・業務再開可否 | 実行前に決める | 実行前に決める |

現時点では確認体制が未設定なので、実行日までに少なくとも「実行する人」「数字と例外を照合する人」「中止・復旧を判断する人」を記録する。いずれかが未定なら、手順を開始しない。

## 3. 実行時の順序

次は将来の実行手順であり、今回の実行記録ではない。

1. A/B2の小売書込み、定期処理、蔵連携を止め、既存利用者に再開時刻が未定であることを周知する。共有DB構成のため、対象外会社・酒蔵への書込みも同じ時間帯に確認する。
2. A と B2 で別々に、配布コミット、PHP/Composer、3 migration の状態、`retail` 接続先、25表の列構成を確認する。前提が一つでも異なれば停止する。
3. 各環境の論理DBバックアップを採取して復元可能性を確認し、B2では `retail:tamagawa-release export` で取込前成果物を採取する。ハッシュを記録してから先へ進む。
4. A に固定コミットを配布し、上記3 migrationを番号順に適用する。migrationの適用だけでは玉川の会社設定・顧客・商品・履歴を変更しない。
5. A で原本・計画・対応表・対象外参照・取込先直前ハッシュを再照合する。承認済みの対応表だけを使い、`retail:tamagawa-release import ... --apply` を一度実行する。商品は未有効、履歴は原値台帳のままとし、通常売上・在庫・請求・蔵受注を生成しない。
6. A の取込後成果物を採取し、B2に同一コミットと同じ3 migrationを適用する。B2で取込を再実行しない。A成果物とB2直前成果物のハッシュを指定して `retail:tamagawa-release restore ... --apply` を一度実行する。
7. A/B2各々で、玉川の顧客数、対象期間の原値合計、開始残高候補、例外73件、在庫/通常売上/請求/入金/蔵受注が自動生成されていないこと、桜浜・他社・共有在庫・酒蔵データの不変を照合する。照合者が再開を記録するまで書込みを再開しない。

工程③で検証した値は、顧客候補6,604件（空の旧ID 1件を保留）、運用開始後売上 1,390,209.0000円、符号付き入金 -511,222.0000円、開始残高候補 5,378,898.4000円、例外73件である。実行時には最終締切時点の再計画を作成し、その値と原本SHA-256を改めて固定する。

## 4. 中止・復旧の条件

- migration前、取込前、復元前の各ゲートでハッシュ・列構成・対象外参照が一致しなければ、書込みなしで中止する。
- migration適用後にデータを書き込む前の不具合は、各環境の論理バックアップからその環境だけを復旧する。新migrationを安易に `migrate:rollback` して共有DBの列を消さない。
- 玉川の取込・復元中に例外が起きた場合、処理は単一トランザクションをロールバックする。復旧手順を続ける前に、直前exportのハッシュと対象外不変を再確認する。
- 業務再開後に新規取引が一件でも発生した場合、古い成果物による上書き復元はしない。中止判断者が、影響範囲を確認した上で別の復旧計画を作る。
- AとB2を同一の復元単位にせず、それぞれのバックアップ・成果物・実行記録で戻す。桜浜、他社、共有在庫、酒蔵、認証・監査、採番は玉川復元の対象外である。

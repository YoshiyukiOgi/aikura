## 3. 歴史データの変換仕様

### 期間と残高

今回の読取検証条件は参照履歴開始2026-06-01、運用開始2026-07-01、取得締切2026-09-23。酒蔵側の6月の保存履歴と7月の運用境界を分けた工程②の結果に基づく。最終実行時には酒蔵リリースと締切を照合して固定する。

開始残高候補は運用開始より前の全明細を顧客別に集計し、元クエリと同様に存在する顧客だけを結合する。6月分の参照履歴を開始残高に再加算しない。運用開始後の数量×単価を符号付きで加算して指定日残高の候補を再現する。集計一致だけで業務上の残高承認済みとはしない。

### 売上・返品・入金・請求

- 元明細ID、元伝票番号、元顧客/商品ID、日付、原数量・単価・摘要・戻入フラグを保存する。負額を全て返品と判定せず、二重符号反転をしない。
- 商品ID=-1は入金として分離。負額を一括絶対値変換しない。入金明細を通常の商品売上・蔵受注へ渡さない。
- 税内訳は `tax_state=unknown`、税額はnull。現在の価格・税率や原本の設定5%で再計算しない。
- B1にない請求確定番号・請求状態・請求別消込・入金方法・現金/掛売区分を生成しない。履歴を原値台帳で保持し、確認できた対応だけを業務表へ反映する。
- 台帳は常に `review_required` の検討候補。計画ハッシュは内容一致の確認であり、業務承認・本番実行の許可ではない。

### 商品・価格・仕入先・発注

- 商品ID=-1を通常商品へ登録しない。残り610商品のItaro同番号は対応候補であり、蔵商品・単位・価格の一致を確認して対応表を固定する。
- 「小売独自商品」フラグは入金用商品に立っているため、外部商品分類に使わない。分類不明・単位不明の商品の本取込は保留する。
- 発注先商品データ380行は商品・価格資料として保持する。確定した注文伝票へ変換しない。
- Tamagawaの発注クエリは変更日の販売から蔵連携対象を作る。調査時の未送信候補は0件。保存されていない過去の送信完了状態を補わず、通常業務で発生する新しい発注と区別する。
- 価格・仕入先等の補助表も計画の原値・差分対象に含める。資料の保存と、営業マスターへの適用が済んだことを混同しない。

## 4. 分離復元の設計

| 区分 | 玉川を選ぶ条件 | 対象外の扱い |
| --- | --- | --- |
| 会社・会社設定・原値台帳 | `company_key=maru` | batsu・sankakuは保持 |
| 顧客・販売 | 玉川会社ID | nullや他社所属を再割当しない |
| 販売明細 | 玉川販売ID | 他社販売明細を保持 |
| 請求・入金 | 玉川顧客ID。共有顧客の参照がないことを検査 | 他社販売・消込との交差があれば停止 |
| 請求明細・消込 | 玉川親ID、かつ販売・請求への参照も玉川内 | 片側だけの削除・復元を行わない |
| 納品・明細・調整 | 玉川販売/顧客を親に選び、関連販売・明細も玉川内 | 交差参照・所有不明は停止 |
| 発注・明細 | 新規会社IDとその親子関係 | 会社IDのない既存発注は除外・個別確認 |
| 商品・仕入先・価格履歴等 | 共有行として必要IDと期待値を個別列挙 | 全行置換しない。衝突を自動上書きしない |
| 在庫・移動 | 移行しない | 全会社の既存値を保持 |
| 採番・同期設定・システム設定 | 共有資源として扱う | A値へ巻き戻さない。全会社のID/採番を考慮して衝突防止 |
| 酒蔵・認証・監査・既存Access対応表 | 復元対象外 | 行・参照ID・動作の不変を照合 |

業務データの完全復元は、対象行と共有依存の検査→復元先直前状態の固定→対象書込み経路停止→対象範囲の保全→依存順で復元→参照・金額・対象外不変の照合、の順序とする。自己参照を含め、ID衝突時に対象外行を削除して合わせない。中断時はトランザクションを戻し、共有コードを戻す場合の互換性も確認する。共有Redis全消去・DB全体のclean・対象外へ及ぶCASCADEは用いない。

`TamagawaScopedRestore` は小売25表（工程②の24表＋原値台帳）の列構成を照合し、玉川所有行の削除・再投入・照合を一トランザクションで行う。共有商品等のID・内容が衝突すれば全体を戻す。復元先にない確認済み商品・仕入先の追加も検証した。酒蔵商品・取引先・受注・受注明細のIDと識別列を照合してから書き込む。現在の共有DB/public構成を前提とし、別DB構成への変更は再設計が必要。

DBのIDシーケンスは全行の最大IDと現在値を比較し、必要な場合に前進させる。伝票採番カウンターや在庫は戻さない。PostgreSQLのシーケンス操作はトランザクションで巻き戻らないため、障害時に欠番が残る可能性はあるが、他社IDへ巻き戻さない。共有資源の書込みと酒蔵参照の更新を止める時間帯は、実行前に決める。

## 7. 次工程で用いる操作と入力

以下は操作仕様であり、今回稼働環境で実行したコマンドではない。

事前保全したB2成果物は逆向きのrestoreにも用いる。復旧直前の状態を再exportしてexpected-targetを固定し、古い確認値を流用しない。業務再開後の新規取引がある場合は単純な上書き復旧を行わない。

顧客コードは既存規則の `TAMAGAWA-C-旧ID（最低4桁）`、商品コードは `TAMAGAWA-P-旧ID`、仕入先コードは `TAMAGAWA-S-確認済みキー`。初回以外の顧客取込は新規旧IDだけとし、変更・削除は自動適用しない。マスター変更・削除を伴う差分は、個別の適用・復旧方法を追加してから扱う。

実行前に、原本と成果物のハッシュ、コード版、DB列構成、対象外参照、非内部トリガーの追加がないこと、共有ジョブと連携の停止、復元可能なバックアップを照合する。テスト合格だけでこれらを省略しない。

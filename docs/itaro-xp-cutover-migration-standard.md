# Itaro-XP 切替移行標準

## 1. 目的

この文書は、Itaro-XP を使用している酒蔵から本システムへ移行する際の標準方針を定める。
特定の酒蔵、PC、ファイルパス、年月日に依存させず、移行開始日を変えて再利用できる手順とする。

対象とする移行方法は次の3種類である。

1. 全く白紙の新システムへ移行する。
2. 試行移行などで重複・不整合があるシステムを白紙化して再移行する。
3. 運用開始後に、開始日より前の履歴を参照専用データとして追加する。

## 2. 基本変数

移行処理では日付をコードへ直接書かず、必ず次の変数として指定する。

| 変数 | 意味 |
|---|---|
| `CUTOVER_DATE` | 新システムで通常運用を開始する日 |
| `OPENING_DATE` | 開始売掛の基準日。通常は `CUTOVER_DATE` の前日 |
| `STOCK_AS_OF_DATE` | Itaro-XPの在庫スナップショットを登録する基準日。通常は最新抽出日 |
| `SOURCE_PATH` | Itaro-XP 原本のパス |
| `ARCHIVE_PATH` | 原本、抽出パッケージ、照合結果、バックアップの保管先 |
| `BREWERY_CODE` | 移行対象の酒蔵を識別するコード |

例として7月1日から運用する場合、`CUTOVER_DATE` は7月1日、`OPENING_DATE` は6月30日となる。
実際の日付は移行案件ごとに決定する。

## 3. 確定した設計方針

### 3.1 運用データ

- `CUTOVER_DATE` 以降の出荷、入金、販売外出入を通常の業務テーブルへ移行する。
- 得意先、商品、単位、価格、税区分など、運用に必要なマスターを移行する。
- `OPENING_DATE` 時点の売掛残高を開始残高として登録する。
- `STOCK_AS_OF_DATE` 時点のItaro-XP在庫を開始在庫として1回だけ登録する。
- 移行した過去の出荷・販売外出入は履歴扱いとし、開始在庫へ重ねて在庫移動を生成しない。
- 請求計算、請求確定、月次締め、税務確定は、移行処理から自動実行しない。
- 請求計算は件数・金額・在庫・売掛の照合完了後、利用者の明示的な指示で行う。

### 3.2 過去履歴

- `CUTOVER_DATE` より前の明細を通常の業務テーブルへ大量投入しない。
- 過去分は現在在庫、現在売掛、請求対象などの運用計算へ影響しない参照専用履歴とする。
- 統計用の集計データと、証拠用の元明細を分けて保管する。
- Itaro-XP 原本は変更せず、ハッシュ値とともに永続保管する。

### 3.3 重複防止

- 見た目の「同日・同商品・同数量・同金額」だけで重複判定しない。
- 出荷伝票番号、出荷明細ID、入金ID、販売外出入IDなど、Itaro-XP の旧IDを正とする。
- 旧IDには一意制約を設定し、再実行時は追加ではなく upsert または置換として扱う。
- 元データに別IDで存在する同一内容の明細は、原則として別取引として保持する。
- 重複候補を削除する場合は、旧ID、元データ件数、金額、参照関係を確認する。

### 3.4 再実行と差分同期の整合性

過去の移行で二重登録が発生した事実を重要な再発防止事項として扱う。
初期移行、白紙化再移行、差分同期のすべてで、次を必須条件とする。

- 同じ移行パッケージを2回適用しても、件数、数量、金額、在庫、売掛が増減しない。
- 移行済み明細を再処理するとき、既存の最大行番号の後ろへ明細を追加しない。
- 出荷明細は旧明細IDを基準に更新し、変更された伝票を「既存明細を残したまま追加」で処理しない。
- 入金は旧入金ID、販売外出入は旧在庫出入IDと旧明細キーを基準に更新する。
- 旧IDが空欄、重複、別取引へ付け替わっている場合は自動反映せず停止する。
- 取込前に、元データと移行先の旧ID重複、件数、数量、金額を検査する。
- 取込後に同じ検査を再実行し、差異がある場合は移行バッチ全体を確定しない。
- 追加・変更・削除は1つのトランザクションまたは復元可能な単位で処理する。
- 途中失敗後の再実行は、未完了バッチへの追記ではなく、ロールバックまたは安全な再適用として行う。
- DBの一意制約とアプリケーション側の事前検査を併用し、どちらか一方だけに依存しない。

差分同期では、前回と今回のItaro-XPスナップショットを
`元テーブル + 旧ID + 内容ハッシュ` で比較し、`new / changed / deleted / unchanged`
へ分類する。`changed` と `deleted` は、請求、在庫、税務、返品、締めへの参照を確認し、
安全に置換できない場合は自動処理せず承認対象とする。

## 4. 白紙から始める移行

### 4.1 事前準備

1. `CUTOVER_DATE`、`OPENING_DATE`、対象酒蔵、対象会社を決定する。
2. Itaro-XP への入力停止時刻を決める。
3. 新システムへの入力を停止する。
4. DB全体を復元可能な形式でバックアップする。
5. Itaro-XP 原本を読み取り専用で複製し、SHA-256を記録する。
6. アプリケーションとDBスキーマを移行ツール対応版へ更新する。

### 4.2 抽出と事前検証

1. Itaro-XP 原本から移行パッケージを作成する。
2. テーブル定義、行数、ファイルハッシュ、旧IDの一意性を検証する。
3. `OPENING_DATE` 時点の売掛残高と、`STOCK_AS_OF_DATE` 時点の在庫を抽出する。
4. `CUTOVER_DATE` 以降の出荷・入金・販売外出入を抽出する。
5. 出荷金額、消費税、酒税、入金額、在庫増減を事前集計する。
6. エラーが1件でもある場合は、業務テーブルを変更せず中止する。

### 4.3 投入

1. 得意先、商品、単位、価格、税区分などのマスターを投入する。
2. `STOCK_AS_OF_DATE` 時点の開始在庫を商品・ロット・保管場所単位で投入する。
3. `OPENING_DATE` 時点の開始売掛を得意先単位で投入する。
4. `CUTOVER_DATE` 以降の出荷を投入する。
5. `CUTOVER_DATE` 以降の入金を投入する。
6. `CUTOVER_DATE` 以降の販売外出入を投入する。
7. `STOCK_AS_OF_DATE` より後の通常運用分だけ、出荷・販売外出入から在庫移動を生成する。
8. 請求計算前の状態で停止する。

### 4.4 照合

- 元データと移行後の旧ID集合が一致する。
- 出荷ヘッダー件数、明細件数、数量、売上額、消費税額が一致する。
- 入金件数、入金額、手数料・調整区分が一致する。
- 販売外出入の件数、増加数量、減少数量が一致する。
- 開始在庫と移行後在庫が、商品・ロット・保管場所単位で一致する。
- 開始売掛と、出荷・入金反映後の得意先別売掛が一致する。
- 酒税区分別の課税移出数量、軽減、控除、税額が一致する。
- 消費税率・課税区分別の売上額と税額が一致する。
- 旧IDの重複が0件、参照切れが0件である。
- 請求書、入金予定、月次締めが意図せず作成されていない。

## 5. 既存システムを白紙化して再移行する場合

試行移行や不完全な再取込によって重複・不整合がある場合は、個別修正を繰り返すより、
取引データを白紙化して再移行する方が安全な場合がある。

### 5.1 白紙化の対象

案件で明示的に承認された場合、手入力・取消済みを含めて次を白紙化できる。

- 出荷ヘッダー・出荷明細
- 請求書・請求明細・請求書出力履歴
- 入金予定・入金消込・入金
- 販売外出入ヘッダー・明細・訂正履歴
- 出荷・販売外出入に由来する在庫移動
- ロット引当・在庫予約
- 月次在庫・月次売掛
- 酒税・消費税の月次ドラフトおよび確定データ
- 移行処理で作成された開始残高

監査ログ、DBバックアップ、Itaro-XP 原本、移行パッケージ、照合結果は削除しない。

### 5.2 削除順序

外部キーと監査性を守るため、概ね次の順で削除する。

1. 帳票出力履歴
2. 入金消込
3. 入金予定
4. 請求明細・請求書
5. 返品・訂正・取消に関する派生データ
6. ロット引当・在庫予約
7. 出荷・販売外出入に由来する在庫移動
8. 出荷明細・出荷ヘッダー
9. 販売外出入明細・ヘッダー
10. 入金
11. 月次残高・税務月次データ
12. 移行マッピングと開始残高

実際の削除前には、DBスキーマから参照関係を再取得し、対象件数を固定する。
削除はトランザクション内で行い、想定件数と異なる場合は全体をロールバックする。

### 5.3 再移行の安全条件

- 削除前に最新のItaro-XP抽出パッケージが検証済みである。
- 削除後に初めて抽出を始める運用は禁止する。
- 削除前後の件数・金額・旧ID一覧を保存する。
- 途中失敗時は部分修正せず、バックアップへ復元して再実行する。
- 作業完了まで対象期間への新規入力を禁止する。

## 6. 過去履歴を後から追加する方法

過去履歴は、運用DBを重くせず、集計・統計・税務確認に利用できる形で追加する。

### 6.1 集計用履歴

DBには少なくとも次の月次集計を保持する。

- 得意先別・商品別の出荷数量、売上額、消費税額
- 得意先別・入金方法別の入金額
- 商品別・ロット別・処理区分別の販売外出入数量
- 得意先別月末売掛残高
- 商品・ロット・保管場所別月末在庫
- 酒類区分・税区分別の課税移出数量、軽減、控除、酒税額
- 消費税率・課税区分別の売上額、消費税額

### 6.2 証拠用履歴

伝票単位の確認に備え、次を圧縮した参照専用ファイルとして保管する。

- Itaro-XP 原本
- 抽出した全明細
- テーブル定義
- 元ファイルと抽出ファイルのSHA-256
- 行数、金額、数量の照合結果
- 移行ツールと抽出ツールのバージョン

形式は圧縮CSV、NDJSON、Parquetなど、将来読み直せる公開形式を優先する。
過去履歴の追加処理は、現在在庫、現在売掛、請求対象、月次締めを変更してはならない。

### 6.3 統合参照

統計・税務画面では、過去の集計用履歴と `CUTOVER_DATE` 以降の運用データを合算する。
運用上の残高計算は `CUTOVER_DATE` 以降だけを対象とし、過去履歴を二重加算しない。

## 7. 他の酒蔵への展開要件

移行ツールは次の引数を持つ構成を目標とする。

```text
--source=<SOURCE_PATH>
--brewery=<BREWERY_CODE>
--cutover-date=<CUTOVER_DATE>
--opening-date=<OPENING_DATE>
--archive-path=<ARCHIVE_PATH>
--mode=fresh|reset|history
--include-manual
--dry-run
--no-billing
```

- `fresh`: 白紙のシステムへ初回移行する。
- `reset`: 既存取引を承認済み範囲で白紙化して再移行する。
- `history`: 開始日前の参照専用履歴を追加する。
- `dry-run`: 削除・更新せず、対象件数と照合結果だけを出力する。
- `no-billing`: 請求計算・確定・締めを実行しない。移行時の既定値とする。

酒蔵ごとの差異は設定ファイルに分離し、移行コードへ会社名、日付、PC名、ファイルパスを直接記述しない。

## 8. 完了条件

次をすべて満たした時点で移行完了とする。

1. バックアップからの復元手順を確認済みである。
2. 抽出・投入・照合結果が保存されている。
3. 旧IDの重複と欠落が0件である。
4. 在庫と売掛がItaro-XPの基準値と一致する。
5. 税務集計が保存値と一致する。
6. 請求計算前の状態である。
7. 利用者が照合結果を承認している。
8. Itaro-XP 原本と履歴アーカイブが保全されている。

## 9. 禁止事項

- バックアップ前に白紙化しない。
- 抽出・検証完了前に現データを削除しない。
- 同じ日付・商品・数量・金額だけで重複削除しない。
- 移行処理から請求計算や月次締めを自動実行しない。
- 開始日前の履歴を現在在庫・現在売掛へ直接加算しない。
- Itaro-XP 原本を更新、上書き、削除しない。
- エラーを無視して部分移行を確定しない。

## 10. 実装済みコマンド

検証済みバッチに対して、まず `--commit` なしで削除対象件数を確認する。

```powershell
docker compose exec -T app php artisan aikura:access-cutover-initialize 5 `
  --cutover=2026-07-01 `
  --opening-date=2026-06-30 `
  --stock-as-of=2026-07-31
```

バックアップと表示件数を確認後、同じコマンドへ `--commit` を追加する。処理は単一トランザクションで行われ、件数または旧ID重複検査が不一致なら全変更をロールバックする。請求計算・請求確定・月次締めは実行しない。

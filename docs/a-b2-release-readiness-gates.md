# A-B2 完全移行の実行条件

この文書は、B1からAへの検証とAからB2への完全昇格を安全に進めるための必須ゲートである。前のゲートが未完了の間、次のゲートの破壊的操作を実行してはならない。

本番開始前はB1を日々の取引・ロット・入出庫・入金の唯一の業務正本とする。AはB1の初回基準取込後、定期差分を取り込み、Aで月次処理・帳票・業務検証を行う環境とする。Aへの実業務の手入力、外部連携による登録は行わない。B2は検証済みのA全体を完全昇格して検証する環境とし、B2だけに恒久データを作らない。

## G1. ロット在庫スキーマ

- 在庫の正本は `stock_movements`、月次確定値は `stock_lot_monthly_balances` である。
- `production_lots.product_id`、`stock_movements.product_id`、商品別在庫予約、商品別月次在庫は存在しない。
- 商品・税務情報を取引履歴に残す場合も、在庫残高の集計キーに使用しない。
- ロット在庫スキーマ、月次作成、月次確定、月次API、月次ジョブの自動テストが成功する。

## G2. 在庫業務フロー

- 入庫、出荷、出荷取消、棚卸調整、販売外出入、返品、ロット引当、品出から出荷までをロット付き在庫移動で検証する。
- 旧商品別残高を参照するコード・Seeder・帳票を廃止またはロット集計へ置換する。
- 各フローで、物理在庫、引当数量、利用可能数量、月次確定後の変更禁止を照合する。

## G3. B1-A データ検証

- B1 Access原本は読取専用で抽出し、原本SHA-256、抽出行数、取込バッチIDを保存する。
- 初回だけ承認済みの基準バッチをAへ取り込み、以後は固定した基準バッチとの差分を `Plan -> CSV確認 -> Apply` の順で取り込む。Aの月次確定値、帳票出力、監査記録を白紙化しない。
- 取引の `changed` / `deleted`、または月次確定済み期間へ影響する差分は自動適用しない。影響範囲、月次解除・訂正・再集計手順を示し、個別承認を得る。
- 差分適用前に、B1原本ハッシュ、比較元・対象バッチ、差分CSV、件数、対象期間、Aバックアップと復元手順、承認をそろえる。
- Aへ投入する前にロット対応不能、単位不一致、数量・金額・税額差異を隔離し、業務在庫へ自動投入しない。
- AでB1との伝票件数、数量、金額、酒税、開始在庫を照合し、利用者が結果を承認する。

## G4. A リリース候補

- 全自動テストが成功する。失敗を例外にする場合は、対象、影響、期限、承認者を記録する。
- AのDBダンプ、アプリ成果物、環境設定の識別子、SHA-256、復元手順を同じリリース記録に固定する。
- 外部メール、API、キュー、スケジューラを止めた状態で復元検証を行う。

## G5. B2 完全昇格

- B2のPostgreSQL、添付ファイル、設定のバックアップと復元確認を完了する。
- 明示承認後にのみ、固定済みのA成果物をB2へ配置し、Aの論理DBダンプを復元する。
- B2でスキーマ、在庫、業務画面、帳票、税務、監査ログ、バックアップを受入検証する。
- B1の停止と本番切替は、B2の受入承認後にB1入力を停止し、停止直後の最終差分をAへ取り込み、月次・在庫・売掛・税額を照合してから実施する。

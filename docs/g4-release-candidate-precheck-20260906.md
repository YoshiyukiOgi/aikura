# G4 Aリリース候補 事前確認記録（2026-09-06）

## 判定

G4は**停止**とする。AのDBダンプ、アプリ成果物の固定、環境設定の固定、復元リハーサル、外部連携停止、B2への操作は実施していない。

## 停止理由

1. G2のロット在庫業務フロー検証が未完了である。
2. G3は機械検証まで完了したが、B1との業務照合および利用者承認が未完了である。
3. 専用の `aikura_testing` データベースで全自動テストを実行し、失敗を確認した。少なくとも、出荷取消、在庫業務、請求、売掛、消費税月次、帳票生成、品出・出荷連携の領域で失敗が残っている。
4. 作業ツリーに未コミットのプログラム、テスト、設計文書、DB migrationの変更がある。コミット識別子を持たない成果物はリリース候補として固定できない。

## 実施済みの安全確認

- テストはDockerの一時 `test` コンテナと `aikura_testing` DBだけで実行した。Aの業務DB、B1、B2は変更していない。
- Access移行検証器の対象テストは3件・18アサーションが成功し、警告を原本行へ追跡する修正の書式検査も成功した。
- Aの通常コンテナ構成では、QueueはRedis、Schedulerは `php artisan schedule:work` で動作することを確認した。復元リハーサルを行う時点でのみ、Web、Queue、Scheduler、外部メール・APIを明示的に停止または検証設定へ切り替える。

## G4を再開する条件

1. G2の必須業務フローをロット在庫方式で完了し、関連テストを成功させる。
2. G3の警告を業務確認し、B1とAの件数・数量・金額・酒税・開始在庫を照合して承認する。
3. 全自動テストを専用DBで成功させ、例外がある場合は対象、影響、期限、承認者を明記する。
4. 変更をレビューしてコミットし、コミットIDを固定する。
5. 固定済みコミットから、A DBダンプ、帳票・添付、設定識別子のSHA-256を同一のリリース記録へ記載する。
6. 稼働中のAではなく隔離した検証環境で、外部連携を止めた復元リハーサルを行い、復元後のスキーマ、在庫、帳票、監査ログを確認する。

# B1-A-B2 移行・本番化セキュリティ方針

> 現行の在庫設計は `lot-inventory-architecture.md` を正とする。旧商品在庫方式はB1原値との照合・監査専用に分離し、A/B2の業務在庫、API、帳票、バッチの計算には使用しない。

## 1. 目的と適用範囲

本書は、現行の Itaro-XP Access データを、新しい酒蔵販売業務システムへ段階的に移行し、検証を経て B2 を本番化するための運用方針を定める。

対象は、Access 原本、移行パッケージ、PostgreSQL、アプリケーションコード、帳票・添付ファイル、設定、SSH 接続、AI を含む移行作業である。

本書と実装済みの移行コマンドに差異がある場合、実行前に差異を明示し、承認を得る。既存の移行仕様は `itaro-xp-cutover-migration-standard.md`、Access 抽出・差分取込の実装範囲は `access-migration.md` を参照する。

## 2. 環境の定義

| 環境 | 役割 | データの正 |
| --- | --- | --- |
| B1 | 現行 Itaro-XP。切替まで通常業務を継続する原本環境 | 切替前の業務データ |
| A | ローカル開発・統合検証環境。コード、DB構造、移行処理を変更・検証する | 検証期間中はB1スナップショットと開発成果 |
| B2 | 本番候補環境。数か月の業務・画面・帳票・復旧検証を行い、そのまま本番化する | 検証期間中はAから完全昇格したB1由来の検証データ |

B1 が稼働中は、B1 の業務データだけを正とする。B2 を本番化した後は、B2 を業務データの正とする。

## 3. 移行の基本原則

1. 本番開始前の B1 から A への移行は、Access 原本を読取専用でコピーして抽出し、ハッシュ、行数、検証結果を記録する。初回は承認済みの基準バッチを取り込み、以後は定めた頻度で B1 差分を A へ適用する。
2. A から B2 へは差分同期を行わず、検証済みのアプリケーション版、DBスナップショット、必要な帳票・添付ファイルを一体として完全昇格する。
3. A の PostgreSQL ダンプ、Git コミット、B1 原本 SHA-256、Access 移行バッチ ID を一組のリリース証跡として記録する。
4. B2 は、次回の A からの完全昇格で再構築される環境とする。B2 だけで行った恒久的なデータ修正は認めない。
5. B2 で残す必要がある検証結果またはデータ修正は、先に A で再現、検証、記録してから、次の完全昇格へ含める。
6. B1 の停止前に、最終 Access スナップショットを A へ取込み、全照合を完了した最終 A リリース候補を B2 へ完全昇格する。

### 3.1 検証期間中のB1差分同期と月次処理

1. 本番開始までは、実取引、ロット、入出庫、入金の正本を B1 のみとする。A と B2 で実業務の入力、外部連携による登録を行わない。
2. Aでは、B1から取り込んだデータを基に月次処理、帳票、在庫・売掛・税額の検証を行う。これらのA固有の月次確定値、帳票出力、監査記録は、通常のB1差分適用で削除または上書きしない。
3. 各検証回は、B1スナップショット取得、ステージング・警告分類、差分計画、差分CSV確認、Aバックアップ、承認済み差分適用、B1-A照合、A-B2完全昇格、B2受入検証の順で実施する。
4. B1取引の `changed` / `deleted`、またはAで確定・締め済みの月へ影響する `new` は自動適用しない。Aの月次解除、訂正取引、再集計の要否と影響を提示し、個別承認後に処理する。
5. AまたはB2の検証で見つけた修正は、データを直接補正して残さず、Aのコード、スキーマ、移行規則または照合規則として再現可能にする。
6. B1の入力停止は最終切替時だけとする。最終回はB1停止直後の差分をAへ取り込み、照合済みのAを完全昇格してからB2を業務正本へ切り替える。

## 4. 通常の検証サイクル

1. A でプログラム、DBスキーマ、移行処理を変更し、自動テストを実行する。
2. B1 の Access 原本を更新せずに一時コピーし、SHA-256 を記録して A へ抽出する。
3. A でステージング、差分計画、件数・金額・在庫・売掛・税額の照合、画面・帳票の検証を行う。警告、取引の変更・削除、締め済み月への影響は個別に分類し、未承認のものを自動適用しない。
4. A をリリース候補として固定する。Git コミット、migration 状態、B1 原本ハッシュ、移行バッチ ID、DBダンプハッシュを記録する。
5. B2 を保守状態にし、Web、Queue、Scheduler、外部連携を停止または検証用設定へ切り替える。
6. B2 の現状態をバックアップする。対象は PostgreSQL、帳票、添付、環境設定、Docker・Webサーバー設定である。
7. A のコードを同一コミットで B2 へ配備し、A の PostgreSQL 論理ダンプを B2 へ復元する。帳票・添付は DB と整合する同じ時点のものを同期する。
8. B2 で migration 状態、復元整合性、権限、画面、帳票、業務シナリオ、バックアップからの復元を確認する。
9. 結果、差異、障害、対応を記録し、次の A の修正へ戻す。

## 5. 最終切替

1. 切替日時、担当者、B1入力停止時刻、B2保守時間、復元責任者、連絡手段を事前に承認する。
2. B1 への通常業務入力を停止し、原本を読取専用で複製して SHA-256 を記録する。
3. A で最終移行、検証、照合を完了する。エラーまたは未承認の差異がある場合は切替を中止する。
4. B2 の直前バックアップをサーバー外にも保管し、復元手順を確認する。
5. A の最終リリース候補を B2 へ完全昇格し、DB・帳票・添付・設定の整合を確認する。
6. B2 で最終受入試験を実施し、承認後にサービスを再開する。
7. B1 は停止後も削除せず、原本と移行証跡として読取専用で保全する。

## 6. 変更・削除の禁止と承認

### 6.1 B1 の保護

- 移行作業、AI、管理者作業による B1 の Access 原本、設定、業務データの変更、削除、上書きを禁止する。
- B1 の通常業務入力は、切替まで既存 Itaro-XP の利用者操作だけに限定する。
- B1 から取得するファイルは読取専用コピーとし、原本パス、取得日時、サイズ、更新日時、SHA-256 を記録する。

### 6.2 B2 と本番候補サーバーの保護

- B2 のDB復元、DBスキーマ変更、データ更新・削除、コンテナ再作成、設定変更、ファイル削除、外部連携の有効化は、承認済みのリリース作業だけに限定する。
- B1/B2 に明示的に含まれないサーバー、DB、ファイル、コンテナ、ネットワーク設定は変更・削除を原則禁止する。
- 例外作業は、実行前に対象、理由、影響範囲、実行内容、バックアップ、復元手順、期待件数、確認者を具体的に示し、明示承認を得る。

### 6.3 AI の権限

- AI は B1 では読取操作だけを行う。
- AI は A では、利用者が依頼した開発・検証作業だけを行う。
- AI は B2 では、情報収集、変更案、検証計画、読取操作までを通常権限とする。
- B2 の書込み、復元、削除、デプロイ、設定変更は、対象と操作内容に結び付いた利用者の明示承認がある場合だけ実行する。
- 承認、バックアップ、監査記録のいずれかを確認できない場合は、変更操作を実行せず停止する。

## 7. 承認記録の必須項目

高影響操作の承認は、少なくとも次を含む。

- 対象環境、ホスト、DB名、テーブル、ファイル、コンテナ
- 実行するコマンドまたは操作内容
- 対象Gitコミット、DBダンプのSHA-256、B1原本のSHA-256、移行バッチID
- 変更・削除の予定件数と業務影響
- 実行前バックアップの保存場所、SHA-256、復元手順
- 実行者、確認者、承認日時、有効期限
- 実行結果、照合結果、失敗時の対応

承認は別の操作や後日の操作へ流用しない。対象または内容が変わる場合は再承認を得る。

## 8. 認証情報、通信、データの保護

1. SSH鍵、B1読取、B2デプロイ、DB復元には用途別のアカウントと最小権限を用いる。共用の管理者アカウントを使わない。
2. SSH は秘密鍵認証を使用し、可能な限りパスフレーズ、接続元制限、ホスト鍵の検証、鍵の失効・更新を行う。
3. `.env`、秘密鍵、DBパスワード、APIトークン、顧客情報をGit、チャット、通常ログ、移行CSVへ記録しない。
4. Access抽出パッケージ、DBダンプ、帳票、添付は業務・個人情報を含む機密データとして扱う。転送中はSSH等で暗号化し、保管先、アクセス権、保管期限、削除手順を定める。
5. B1、A、B2 の資格情報と設定は分離する。A の `.env` をそのまま B2 へ複製しない。

## 9. 運用上の追加統制

1. B2 のメール、印刷、外部API、通知、ジョブ、スケジューラは、検証中に実取引先や外部サービスへ影響しない設定にする。
2. B2 のWeb、Queue、Schedulerを停止してからDB復元を行い、復元後に意図しないジョブが実行されないことを確認する。
3. バックアップはサーバー外へ保管し、定期的に別環境で復元テストを実施する。バックアップ取得だけで完了としない。
4. DB、帳票、添付、環境設定、Docker・Webサーバー設定を同じ復元単位として扱う。
5. SSH接続、管理者操作、デプロイ、DB復元、権限変更、失敗した承認試行を監査ログへ記録する。資格情報と不要な個人情報はログに残さない。
6. B2 を本番化する前に、OS・Dockerの更新、ファイアウォール、不要なポート、SSHパスワード認証、監視、障害通知、再起動手順を確認する。
7. 現行のデプロイ方針が想定するOSと、実際にB2で運用するOSが異なる場合は、本番化前に方針、保守方法、復旧方法、責任者を明文化して承認する。

## 10. 実行停止条件

次のいずれかに該当する場合、書込み・削除・復元・デプロイを停止し、原因と必要な判断を報告する。

- 対象環境または対象パス・DB名を確定できない。
- 必要な承認、バックアップ、ハッシュ、復元手順、監査記録が欠けている。
- B1原本、移行パッケージ、DBダンプ、帳票・添付の整合性を確認できない。
- 検証で未承認の件数、金額、在庫、売掛、税額、権限、帳票の差異がある。
- 外部連携、通知、ジョブが意図せず実行されるおそれがある。
